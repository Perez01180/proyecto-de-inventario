0 · ¿Qué es un Router en Express?

🧠 Analogía: El server.js es el portero del edificio. Los routers son los encargados de cada piso: uno atiende autenticación, otro el panel, otro los usuarios. Cada uno sabe lo suyo, no se mezclan.
1

Crear el archivo routes/usuarios.js

Siempre tiene esta estructura:

const express = require('express');
const router  = express.Router();
const db      = require('../db');

// acá van las rutas...

module.exports = router;
2

Registrar el router en server.js

const usuariosRoutes = require('./routes/usuarios'); // 🆕

app.use('/auth',      authRoutes);
app.use('/dashboard',  dashRoutes);
app.use('/usuarios',   usuariosRoutes); // 🆕

⚠️ Las rutas dentro de usuarios.js NO llevan /usuarios. El prefijo ya lo pone server.js.

Encadenar middlewares

Una ruta puede tener varios filtros antes de llegar al código final:

router.post('/', requireAuth, requireRole('admin', 'superadmin'), (req, res) => {
  // si llegó hasta acá: está logueado Y tiene el rol necesario
});

Cada middleware decide si llamar a next() (pasar al siguiente) o cortar la cadena.

⚠️
Los formularios HTML solo soportan GET y POST. Para PUT y DELETE usamos fetch() desde JavaScript.

1 · Middleware de roles — requireRole

🧠 Analogía: Un recital tiene dos controles. Puerta 1: ¿tenés entrada? → requireAuth. Puerta 2: ¿tenés pase VIP para esta zona? → requireRole. Algunas zonas dejan pasar a cualquiera con entrada, otras solo a VIP.
1

¿Por qué necesitamos roles?

No todos los usuarios logueados pueden hacer todo:

  • Un alumno no debería poder borrar a otros usuarios.
  • Un admin no debería poder cambiar roles (solo el superadmin).
  • Algunas rutas son para cualquiera, otras solo para ciertos roles.
2

El código — Lo agregamos en middleware/auth.js

// requireAuth ya lo tenemos (verifica sesión)
function requireAuth(req, res, next) {
  if (req.session && req.session.userId) {
    next(); // logueado → pasar
  } else {
    res.redirect('/login.html'); // no logueado → rebotado
  }
}

// 🆕 requireRole: recibe una lista de roles y devuelve un middleware
function requireRole(...roles) {
  return (req, res, next) => {
    if (roles.includes(req.session.rol)) {
      next(); // su rol está en la lista → pasar
    } else {
      res.status(403).json({ error: 'No tenés permiso para esta acción' });
    }
  };
}

module.exports = { requireAuth, requireRole }; // 🆕 exportamos ambos
3

¿Por qué es una función que devuelve una función?

Porque necesitamos que sea configurable. Cada ruta necesita una lista distinta de roles permitidos:

RutaMiddlewareRoles que pueden
POST /usuariosrequireRole('admin', 'superadmin')admin y superadmin
DELETE /usuarios/:idrequireRole('superadmin')solo superadmin

Si fuera un middleware fijo, no podríamos cambiar los roles permitidos en cada ruta.

2 · GET /usuarios — Listar

🧠 Analogía: Una oficina con empleados. El jefe y el gerente pueden ver la lista completa. El empleado raso solo ve su propia ficha.
1

Comportamiento según el rol

El mismo endpoint GET /usuarios hace cosas distintas según quién lo pide:

  • usuario: solo ve su propio perfil → WHERE id = req.session.userId
  • admin y superadmin: ven todos → SELECT sin WHERE
2

El código

router.get('/', requireAuth, (req, res) => {
  if (req.session.rol === 'usuario') {
    // usuario normal: solo su perfil
    db.query(
      'SELECT id, nombre, apellido, dni, telefono, direccion, usuario, rol FROM usuarios WHERE id = ?',
      [req.session.userId], (err, resu) => {
        if (err) return res.status(500).json({ error: 'Error del servidor' });
        res.json(resu);
      }
    );
  } else {
    // admin y superadmin: ven todos
    db.query(
      'SELECT id, nombre, apellido, dni, telefono, direccion, usuario, rol FROM usuarios',
      (err, resu) => {
        if (err) return res.status(500).json({ error: 'Error del servidor' });
        res.json(resu);
      }
    );
  }
});
3

Dos detalles importantes

  • No lleva requireRole: todos los logueados pueden consultar.
  • No devolvemos la contraseña: el SELECT pide solo id, nombre, apellido, dni, telefono, direccion, usuario, rol.

3 · POST /usuarios — Crear

🧠 Analogía: Solo el gerente (admin) y el jefe (superadmin) pueden contratar gente nueva. El gerente siempre contrata empleados rasos. El jefe puede contratar gerentes también.
1

¿Quién puede crear?

Solo admin y superadmin. Por eso usamos requireRole('admin', 'superadmin').

2

Validación de campos obligatorios

Siempre validamos en el servidor, aunque el frontend también valide. ¿Por qué? Porque el frontend se puede saltar (consola del navegador, Postman). El servidor es la última defensa.

Campo¿Obligatorio?
nombreSí
apellidoSí
usuarioSí
passwordSí
dniNo (opcional)
telefonoNo (opcional)
direccionNo (opcional)
fechaNacimientoNo (opcional)
3

¿Qué rol se asigna al nuevo usuario?

  • Admin crea: el rol se fuerza a 'usuario'. No puede elegir.
  • Superadmin crea: si manda rol en el body, lo usa. Si no, por defecto 'usuario'.
4

El código

router.post('/', requireAuth, requireRole('admin', 'superadmin'), (req, res) => {
  const { nombre, apellido, dni, telefono, direccion, usuario, fechaNacimiento, password } = req.body;

  // 1️⃣ Validar campos obligatorios
  if (!nombre || !apellido || !usuario || !password) {
    return res.status(400).json({ error: 'Nombre, apellido, usuario y contraseña son obligatorios' });
  }

  // 2️⃣ Decidir el rol
  const rolAsignado = (req.session.rol === 'superadmin' && req.body.rol)
    ? req.body.rol : 'usuario';

  // 3️⃣ Insertar en la base de datos
  db.query(
    'INSERT INTO usuarios (nombre, apellido, dni, telefono, direccion, usuario, fechaNacimiento, password, rol) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?)',
    [nombre, apellido, dni || null, telefono || null, direccion || null, usuario, fechaNacimiento || null, password, rolAsignado],
    (err, resu) => {
      if (err) {
        // 4️⃣ Si el usuario ya existe, MySQL tira ER_DUP_ENTRY
        if (err.code === 'ER_DUP_ENTRY') {
          return res.status(409).json({ error: 'El usuario ya existe' });
        }
        return res.status(500).json({ error: 'Error al crear el usuario' });
      }
      res.status(201).json({ success: true, id: resu.insertId, mensaje: 'Usuario creado correctamente' });
    }
  );
});

4 · PUT /usuarios/:id — Modificar

🧠 Analogía: El gerente puede cambiar el sueldo o el horario de un empleado, pero no puede ascenderlo a gerente. Solo el jefe asciende gente.
1

Query dinámica (¿por qué?)

El frontend no siempre manda todos los campos. Si el usuario solo cambió el teléfono, no queremos pisar el resto con vacíos. Armamos el UPDATE concatenando solo lo que vino en el body.

2

Regla crítica: el admin NO puede cambiar roles

Si el body incluye rol pero quien llama NO es superadmin → 403 Forbidden. Esto es seguridad real: no alcanza con ocultar el selector de rol en el frontend.

3

El código

router.put('/:id', requireAuth, requireRole('admin', 'superadmin'), (req, res) => {
  const { nombre, apellido, dni, telefono, direccion, usuario, fechaNacimiento, password, rol } = req.body;

  // 🚫 Admin no puede cambiar roles
  if (rol && req.session.rol !== 'superadmin') {
    return res.status(403).json({ error: 'Solo el superadmin puede cambiar roles' });
  }

  // Armar query dinámica
  let sql = 'UPDATE usuarios SET nombre=?, apellido=?, dni=?, telefono=?, direccion=?, usuario=?, fechaNacimiento=?';
  let valores = [nombre, apellido, dni, telefono, direccion, usuario, fechaNacimiento];

  if (password && password.trim() !== '') {
    sql += ', password=?';
    valores.push(password);
  }

  if (rol && req.session.rol === 'superadmin') {
    sql += ', rol=?';
    valores.push(rol);
  }

  sql += ' WHERE id=?';
  valores.push(req.params.id);

  db.query(sql, valores, (err, resu) => {
    if (err) return res.status(500).json({ error: 'Error al modificar' });
    if (resu.affectedRows === 0) {
      return res.status(404).json({ error: 'Usuario no encontrado' });
    }
    res.json({ success: true, mensaje: 'Usuario modificado' });
  });
});

5 · DELETE /usuarios/:id — Eliminar

🧠 Analogía: Solo el jefe (superadmin) puede despedir gente. El gerente gestiona pero no destruye. Borrar es irreversible.
1

La operación más restrictiva

Usamos requireRole('superadmin') — uno solo. Ni admin ni usuario pasan este filtro.

2

El código (el más simple)

router.delete('/:id', requireAuth, requireRole('superadmin'), (req, res) => {
  db.query('DELETE FROM usuarios WHERE id = ?', [req.params.id],
    (err, resu) => {
      if (err) return res.status(500).json({ error: 'Error al eliminar' });
      if (resu.affectedRows === 0) {
        return res.status(404).json({ error: 'Usuario no encontrado' });
      }
      res.json({ success: true, mensaje: 'Usuario eliminado' });
    }
  );
});
3

Rol¿Puede?
usuario❌ 403
admin❌ 403
superadmin✅
